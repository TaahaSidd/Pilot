Setting up and running Pilot

This covers everything from first run to how the automation loop, quiz solver, and feedback engine actually behave, written against the current implementation, not an idealized one.

Prerequisites

Four things, gathered once:

01
Amity Amigo credentials
Your student email (name@s.amity.edu) and portal password, used to authenticate the browser session.
02
Groq API key
Generated free at console.groq.com, used for quiz inference only.
03
Python 3.8+
Check with python --version.
04
Git
To clone the repository, or download the ZIP from GitHub instead.

Quick start

The first run walks you through onboarding once. Every run after that reads from the saved config.

1. Clone and install

terminal 
# clone the repository
git clone https://github.com/TaahaSidd/Pilot.git
cd Pilot

# install dependencies
pip install -r requirements.txt

# install the Chromium binary Playwright drives
playwright install chromium

2. Run it

terminal 
python main.py

3. Onboarding, first run only

If no user_config.json exists yet, you are prompted for four values, which are then written to disk in that file:

interactive prompts 
Groq API Key
  > gsk_••••••••••••••••••••••••
Amity Student Email
  > user@s.amity.edu
AMIGO Portal Password
  > ••••••••••••
Phone number (for feedback forms)
  > 99999XXXXX

Setup complete, credentials saved locally
Where this is stored

These values are written to user_config.json in plain text, next to the script. Nothing here is encrypted or transmitted anywhere except the Groq key, which is sent with each quiz inference call.

4. Manual CAPTCHA

Pilot opens the login page and fills in your credentials, but the visual CAPTCHA on the Amigo login screen still requires a human. Solve it manually in the open browser window, then return to the terminal.

Manual step required

After solving the CAPTCHA, press Enter in the terminal once you are on the dashboard. This hands control back to Pilot, which then begins the automation loop.

5. Let it run

From here Pilot scans your courses, works through pending modules, and prints a completion summary per course as it finishes. No further input is needed unless a module is skipped, see known limits.

The automation loop

Once logged in, the Workflow class drives every course through the same sequence:

01
Discover courses
Reads each course card's completion percentage from the dashboard and skips anything already at 100% before opening a single module.
02
Map modules
Classifies each module as PAGE, QUIZ, FEEDBACK, RESOURCE, or OTHER by inspecting its link path, and excludes locked modules unless they are a pending quiz or feedback form.
03
Process each pending module
Page modules are read into a short-term context buffer. Quizzes pass that buffer to the solver. Feedback forms are filled and submitted field by field.
04
Re-scan, up to 10 passes
Completing a module can unlock another. After each pass the module list is re-fetched; if the pending count does not change between two consecutive passes, the loop exits early instead of running to the limit.
05
Advance
Once a course has zero pending modules, Pilot moves to the next one. The run ends when every discovered course has been visited.

Quiz solver

QuizSolver reads the active quiz's question and options, combines them with up to 3,000 characters of preceding page content as context, and sends that to Groq's Llama 3.3 70B for resolution.

quiz_solver.py, simplified 
payload = {
  "model": "llama-3.3-70b",
  "question": scraped_question,
  "options": scraped_options,
  "context": reading_material_buffer[:3000]
}

answer = groq.infer(payload)
# selected option is clicked and submitted

Guardrails

The solver skips a module instead of guessing when:

  • The question text or answer options cannot be located on the page
  • The layout does not match the expected quiz structure
  • Fewer answer options are found than the question requires

In each case it logs a warning and moves on, rather than submitting a low-confidence answer.

Feedback engine

FeedbackSolver exists because feedback forms gate progression, without resolving them, the course tree stops unlocking. It walks the form field by field:

01
Country or region dropdown
Selected first, separately from generic dropdowns, since it is the most common required field.
02
Remaining dropdowns
Each select gets its first non-empty, non-placeholder option.
03
Radio groups
Resolved to the highest non-zero value in the group, excluding any "not selected" option, not a fixed score.
04
Checkboxes
The first checkbox in each group is selected.
05
Text fields and text areas
Filled with context-aware defaults guessed from the field's label, like phone number, industry, department, or a general course-feedback sentence for open text areas.

Once every detected field is filled, the solver locates the submit button and clicks it. If the submit button cannot be found, it logs a warning and does not submit.

Known limits

  • Built specifically for Amity Amigo's current Moodle theme, selectors throughout the workflow layer assume that markup, so pointing Pilot at another portal will not work.
  • Login still requires a human to solve the CAPTCHA once per session.
  • If a course dashboard returns zero course buttons on scan, it usually means the page had not finished rendering, or the dashboard markup has changed, see the project's GitHub issues for current workarounds.
  • Text-field defaults are reasonable guesses, not verified facts, review feedback responses if accuracy matters for a specific course.
